## 1. プロジェクトライセンス

### 現状

- 要件定義 3章は「Apache-2.0候補。依存ライブラリとモデル重みのライセンス確認後確定」
- `LICENSE`（PR #80 で追加）は Apache License 2.0 の**抜粋と独自の要約**（第1・2条の一部と URL）で、公式の全文ではない
- GitHub のライセンス判定は `Other`（`gh repo view --json licenseInfo` で確認）。Apache-2.0 として認識されていない

### 問題点

- Apache-2.0 第4条(a)は、再配布時に受領者へ「このライセンスの写し」を渡すことを求める。抜粋は写しにならない
- 第3条以降（特許ライセンスの終了条件、第4条の再配布条件、第7条の保証の否認、第8条の責任の制限）が欠けており、利用者・貢献者がどの条件に従うのか曖昧になる

### 案

| 案 | 内容 | 評価 |
|---|---|---|
| **推奨** | Apache-2.0 で確定し、`LICENSE` を <https://www.apache.org/licenses/LICENSE-2.0.txt> の全文（改変なし）に置き換える。著作権表示が必要なら付録（APPENDIX）の書式に従い、ソースのヘッダーか `NOTICE` に書く | 依存とモデル重みはすべて両立（2章）。GitHub も Apache-2.0 と判定するようになる（推測：判定は licensee による全文照合のため） |
| 代替 | MIT にする | 依存との両立は同じ。Apache-2.0 の特許条項が要らないなら簡素。ただし要件定義 3章の記述変更が必要 |
| 非推奨 | 現在の抜粋のまま | 上記の問題が残る |

`NOTICE` ファイルは Apache-2.0 では任意（第4条(d)は「元の著作物に NOTICE があれば」引き継ぐ義務）。utter 独自の `NOTICE` は必須ではない。

- 追加するときは `exact:` で版を固定し、版を上げるたびにこの表を更新する（[ビルド・配布規約](ビルド・配布規約.md)）

### 2.2 モデル重み・トークナイザー

| 配布物 | 使い方 | ライセンス | 出典 | 両立 |
|---|---|---|---|---|
| OpenAI Whisper のモデル重み | WhisperKit の Core ML モデルの元 | MIT（README「Whisper's code and model weights are released under the MIT License」） | openai/whisper の README・LICENSE | 両立 |
| `argmaxinc/whisperkit-coreml`（Core ML 変換済みモデル） | 取得してローカルで推論 | MIT（Hugging Face のモデルカード `license: mit`） | HF モデルカード（main のコミット `0f63a78`、最終更新 2026-08-19） | 両立 |
| トークナイザー（`tokenizer.json` 等）：`openai/whisper-tiny` / `-base` / `-small` / `-large-v3` | WhisperKit がローカルになければ別リポジトリから取得。variant とリポジトリの対応は `ModelUtilities.tokenizerNameForVariant`（tiny→`openai/whisper-tiny`、base→`-base`、small→`-small`、large-v3 系（turbo を含む）→`openai/whisper-large-v3`） | Apache-2.0（4つとも HF モデルカード） | HF モデルカード | 両立 |

- モデルを utter が**再配布しない**（利用者が HF から直接取得する）場合、モデルの表示義務は取得元が満たしている。ただし謝辞にモデルの出典とライセンスを書いておく（推奨）
- utter の GitHub Releases に**ミラーする**場合は、モデルと一緒に MIT の表示（openai/whisper と argmaxinc の両方）と、**選んだ variant が使うトークナイザーの取得元リポジトリのライセンス表示**を置く。2026-10-18 時点では上の4リポジトリとも Apache-2.0。variant を変えたときや WhisperKit の版を上げたときは、対応表と取得元のモデルカードを見直す（例：`openai/whisper-large-v3-turbo` のモデルカードは MIT だが、WhisperKit v1.1.1 はトークナイザーをそこから取らない）

### 2.3 外部 API

Anthropic API・OpenAI API はライブラリではなく、各社の利用規約に従う（ライセンスの両立の対象外）。SDK は使わず REST で呼ぶ方針（[アーキテクチャ](アーキテクチャ.md)）。

### 2.4 結論

採用済み・候補の依存とモデル重みは、すべて MIT / Apache-2.0 / BSD 型 / zlib 型の許容型ライセンスで、Apache-2.0 のプロジェクトと両立する。コピーレフト（GPL 等）は見つからなかった。義務は**表示の保持**（D-3）に集約される。

## 3. モデル配布（PERM-03）

[ビルド・配布規約](ビルド・配布規約.md) のとおり、モデルはバイナリに同梱せず、初回にユーザー操作で取得する前提で案を比較する。

### 3.1 取得対象のサイズ（事実）

Hugging Face の tree API（`/api/models/argmaxinc/whisperkit-coreml/tree/main/<variant>?recursive=true`）でファイルサイズを合計した値（main のコミット `0f63a78`）。

| variant | ファイル数 | 合計 | うち LFS |
|---|---|---|---|
| `openai_whisper-tiny` | 19 | 76.6 MB | 11 |
| `openai_whisper-base` | 19 | 146.7 MB | 11 |
| `openai_whisper-small` | 19 | 486.5 MB | 11 |
| `openai_whisper-small_216MB` | 19 | 217.4 MB | 11 |
| `openai_whisper-large-v3-v20240930_626MB` | 17 | 626.7 MB | 9 |
| `openai_whisper-large-v3-v20240930_turbo_632MB` | 22 | 645.7 MB | 12 |

これにトークナイザー（`openai/whisper-small` なら `tokenizer.json` 約 2.5 MB ほか数ファイル）が加わる。どの variant を使うかは #49 の検証で決める。

**HF のメタデータで分かる SHA-256 は LFS のファイルだけ**：LFS のファイルは `lfs.oid` が SHA-256 だが、LFS でないファイル（各 variant の 8 ファイル前後とトークナイザー）は git の blob ID（SHA-1）しか返らない。マニフェストの SHA-256 は、固定したリビジョンのファイルを実際に取得して計算する必要がある。

### 3.2 WhisperKit の取得処理の現状

WhisperKit v1.1.1 のソースを読んだ結果（`Sources/WhisperKit/Core/WhisperKit.swift`、`Sources/WhisperKit/Utilities/ModelUtilities.swift`、`Sources/ArgmaxCore/External/Hub/HubApi.swift`）。

- `WhisperKit.download(variant:...)` は `https://huggingface.co` の `argmaxinc/whisperkit-coreml` から取得する。**リビジョンを指定する引数がなく、`main` の最新を取る**
- トークナイザーはローカルの `tokenizerFolder` 等に `tokenizer.json` がなければ、`openai/whisper-*` から取得する
- Hub クライアントは、既存ファイルを再利用するかの判断で ETag（LFS なら SHA-256）と照合するが、**新しく取得したファイルの SHA-256 は照合していない**
- `WhisperKitConfig` には `modelFolder`・`tokenizerFolder`・`download: Bool` があり、ローカルのフォルダを渡せる

このため D-6 の推奨は「utter が固定リビジョンから取得 → ステージング用ディレクトリで `ModelIntegrityVerifier`（PR #112）で照合 → 合格したらモデルのディレクトリへ移動 → `modelFolder` / `tokenizerFolder` を指定し `download: false` で WhisperKit を初期化」。`download: false` とローカルフォルダ指定でネットワークに出ないことは推測で、#49 の検証で通信を監視して確認する（AC-06 の観点でも必要）。

### 3.3 取得元の案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **S1（推奨）** | HF `argmaxinc/whisperkit-coreml` を `https://huggingface.co/argmaxinc/whisperkit-coreml/resolve/<コミットハッシュ>/<パス>` で取得。トークナイザーも `openai/whisper-*` のコミットハッシュで固定 | 配布の手間・費用がない。公式の配布物 | 第三者の可用性に依存。リポジトリが消える・履歴が書き換わると取得できない（検証で失敗するだけで、誤ったモデルはロードしない） |
| S2 | utter の GitHub Releases にミラー（1ファイル 2 GiB 未満の制限内に収まる） | 取得元を自分で管理できる | ミラーの更新・ライセンス表示の手間。`.mlmodelc` はディレクトリのため、アーカイブにするかファイル単位で置くかの設計が要る |
| S3 | S1 を主、S2 を予備 | 可用性が高い | 両方の運用が要る。予備も同じマニフェストで照合すれば安全性は変わらない |

取得元の表示（PERM-03）：取得前の画面に「Hugging Face（argmaxinc/whisperkit-coreml）」「モデル名」「合計サイズ」を表示する。

### 3.4 マニフェストを信頼できる経路で持つ案

`ModelManifest`（PR #112）の注記のとおり、モデルと同じ取得元から同時に受け取ったマニフェストでは改ざんを検出できない。

| 案 | 内容 | 改ざん検出 | モデル更新 | 評価 |
|---|---|---|---|---|
| **M1（推奨）** | マニフェスト（相対パス・サイズ・SHA-256）をアプリのバンドルに同梱する。リリース作業で、固定したリビジョンのファイルを取得して SHA-256 を計算するスクリプトで生成し、レビューしてコミット | できる（バンドルは Developer ID 署名・公証で保護。自前ビルドはソースからの生成物） | アプリの更新が必要 | モデルを変えるときは精度・性能の再計測が要る（AC-19）ので、アプリ更新と一緒で困らない。実装が最も単純 |
| M2 | マニフェストを別配布（GitHub Releases 等）し、Ed25519 で署名。公開鍵をアプリに同梱 | できる | アプリ更新なしで可能 | 鍵の管理（CI の secrets、失効・交換）が増える。今の要件では不要 |
| M3 | 実行時に HF の API から LFS の SHA-256 を取る | できない（同じ取得元） | — | 不採用。LFS でないファイルは SHA-256 が取れない |
| M4 | HTTPS だけに頼り、照合しない | できない | — | 不採用（PERM-03 の「完全性を検証」を満たさない） |

サイズ表示は M1 のマニフェストの `totalByteCount` を使い、取得前に空き容量も確認する（推奨）。

PR #112 で残っている関連の判断（`.DS_Store` などマニフェスト外のファイルを失敗にするか、起動ごとに再検証するか）は、このマニフェストの方式とは独立に決められる。

## 4. 署名・公証

### 4.1 公式バイナリ（Developer ID 署名・公証）

Apple の文書から確認した要件：

- 署名は Developer ID Application 証明書（Apple Development・Ad Hoc・ローカルの開発用証明書は不可）
- Hardened Runtime を有効にし、署名に secure timestamp を含める
- `xcrun notarytool submit` で提出し、`xcrun stapler staple` で公証チケットを付ける。ZIP には付けられないため、`.app` か `.dmg` に付けてから配布物を作る
- `notarytool` の認証は App Store Connect API キー（`--key` / `--key-id` / `--issuer`）か、Apple ID と App 用パスワード（`--keychain-profile` に保存可）
- XPC Worker（`Workers/macOSSTT`）などバンドル内のコードも同じく署名する（推測：Xcode のアーカイブ・書き出しでは内側から順に署名される。ターゲット作成後に `codesign --verify --deep --strict` で確認）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **N1（推奨）** | GitHub Actions のリリース用ワークフロー（タグの push を起点）で、署名・公証・stapler・Releases への添付まで行う | 手順が再現可能。手元の環境に依存しない | 秘密情報を GitHub に置く（下の対策で範囲を絞る） |
| N2 | maintainer の手元 Mac で Xcode Organizer か `notarytool` を使い、成果物を手動で Releases に添付 | 秘密情報が手元から出ない | 手作業。手順の記録と再現性に注意が要る |

N1 での秘密情報の扱い（推奨）：

- Environment（例：`release`）に secrets を置き、**承認者（required reviewers）** を設定する。承認されるまでジョブは Environment の secrets を読めない。デプロイできるタグを `v*` などに制限する
- Environment の secrets：Developer ID の `.p12`（Base64）とそのパスワード、一時キーチェーンのパスワード、App Store Connect API キー（`.p8` の中身）とキー ID・Issuer ID
- 認証は **API キー**を使う（Apple ID の App 用パスワードより、個人アカウントと切り離せて失効させやすい）
- `.p12` は `$RUNNER_TEMP` に復元し、一時キーチェーンに取り込む（GitHub の手順書のとおり）。GitHub ホストのランナーはジョブ後に破棄されるが、セルフホストを使うなら最後に `security delete-keychain` で消す
- リリース用ワークフローは `pull_request` / `pull_request_target` で起動しない。フォークからの PR には secrets が渡らない仕様だが、`pull_request_target` は例外になりうるため使わない
- `.p8` を誤ってコミットしないよう `.gitignore` に `*.p8` を追加する（推奨。現在の `.gitignore` は `*.p12` 等のみ）

Sparkle 2 を入れる場合（後続）：更新アーカイブは Sparkle の EdDSA（ed25519）でも署名する。`generate_keys` の秘密鍵は Developer ID とは別の秘密情報として同じ Environment に置き、公開鍵を `SUPublicEDKey` に入れる。

### 4.2 自前ビルド用の固定署名

Apple TN3127 によると、Accessibility・マイク等の許可（TCC）はアプリの designated requirement（DR）に紐づく。**Ad Hoc 署名（Xcode の Sign to Run Locally）の DR はそのビルドに固有**で、再ビルドのたびに許可が外れる。また、Apple Development で署名したものと Developer ID で署名したものは DR が違うため、自前ビルドから公式バイナリに切り替えると再許可が必要になる。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **L1（推奨）** | Apple Development 証明書（無料の Personal Team で可）で Xcode の自動署名。Team ID は `Local.xcconfig` で上書き | Xcode の標準の流れ。DR は証明書の CN（`Apple Development: …`）と発行元で決まり、同じ証明書なら再ビルドしても変わらない（TN3127 の例） | Apple ID が要る。証明書を作り直したときに DR が変わるか（CN が同じなら変わらないはず）は推測 |
| L2 | キーチェーンアクセスの証明書アシスタントで自己署名のコード署名証明書を作り、それで署名 | Apple ID が要らない | DR の形（推測：証明書そのもののハッシュに紐づく）を確かめていない。証明書を失うと再許可が必要 |
| 不採用 | Ad Hoc 署名 | — | ビルドごとに許可が外れる |

確認手順（ターゲット作成後、#47 か後続の Issue で実施）：

1. 同じ署名で2回ビルドし、`codesign -d -r- <App>.app` の DR が同じことを確認する
2. 1回目で Accessibility・マイクを許可し、2回目のビルドで再要求されないことを確認する
3. L2 も同じ手順で確かめ、結果を README の自前ビルド手順に反映する
