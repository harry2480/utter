# utter 精度評価の手順

[要件定義.md](要件定義.md) 9章・AC-04 の精度評価を、再現できる手順で行うための規則。
計算は `Packages/UtterEvaluation`（`utter-eval`）で行う。規則を変えるときは、この文書とコードとテストを同時に更新する。

> 本書の正規化規則と意味改変の判定基準は、初版の提案である（製品判断として確定が必要）。
>
> 9章の初期目標のうち、フィラー除去成功率と自己訂正成功率の測り方は本書の範囲外（別途定める）。
> 質問文・命令文を含む発話（AC-17, TXT-04）は、該当する区分に含め、回答や実行が混入したら `contentAdded` として記録する。
> これとは別に、回答・実行の応答を棄却できるかを自動テストで確かめる評価セットを持つ（[質問文・命令文の評価セット](#質問文命令文の評価セットac-17)）。

---

## 評価セット

- 区分は 日本語・日英混在・開発用語・数字・自己訂正・騒音 の6つ（JSON では `japanese` / `mixedJapaneseEnglish` / `developerTerms` / `numbers` / `selfCorrection` / `noisy`）
- 各区分 50 発話以上（合計 300 以上、暫定）。結果には区分ごとの件数を必ず併記する
- 評価用音声はリポジトリに含めない（`eval/audio/` は gitignore 済み）。リポジトリで管理するのは正解テキストと結果の JSON、本書の規則だけ
- 実在の個人情報や、他人の実際の発話を正解テキストに含めない

### 結果の JSON

`EvaluationSample` の配列。記入例は [eval/results.example.json](../eval/results.example.json)。

| キー | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 評価セット内で一意な識別子 |
| `category` | ○ | 上記6区分のいずれか |
| `reference` | ○ | 発話どおりの正解。フィラー・言い直しも書き起こす（フィラーを出力しない STT ほど CER が高く出る。この扱いは製品判断として確定が必要） |
| `terms` | | 用語単位で正答率を測る語。`reference` に表記どおり含める |
| `sttOutput` | | STT 単体の結果（未実施なら省略） |
| `refinedOutput` | | AI 整形後の結果（未実施なら省略） |
| `meaningChanges` | | 整形後の結果に対する重大な意味改変の判定。改変なしは `[]`、未判定は省略。`refinedOutput` がない発話には書かない |

### 実行

```sh
swift run --package-path Packages/UtterEvaluation utter-eval eval/results.json
```

区分ごとの件数・CER・用語正答率・重大な意味改変率を Markdown の表で出力する（発話本文は出力しない）。
結果はリリースごとに `docs/計測/` へ記録する（AC-19）。

## CER の正規化規則

正解と STT 結果の両方に、次の順で同じ規則を適用してから文字（書記素）単位の編集距離を数える。
CER = 編集距離の合計 ÷ 正規化後の正解の文字数の合計（発話ごとの CER の平均にはしない）。挿入が多いと 100% を超える。

1. **全角・半角**: Unicode NFKC で正規化する。全角英数字・記号は半角に、半角カナは全角になる
2. **英字の大文字・小文字**: 小文字にそろえる
3. **数字表記**: 漢数字・アラビア数字・位取りの文字（十・百・千・万・億・兆）の並びを1つの数として読み、アラビア数字にそろえる
   - 位取りの文字を含む並びは値として読む（三百二十 → 320、2千 → 2000、3万 → 30000、1億2000万 → 120000000）
   - 位取りのない並びは1文字ずつ置き換える（二〇二六 → 2026）
   - 3桁ごとの桁区切りの `,` は除いて読む（1,200万 → 12000000）。3桁ごとでない `,` は列挙とみなして残す（手順4で除く）
   - 数字を含まず位取りの文字だけの並び（千葉の千、百合の百）は、直後が助数詞（時・分・円・人・個・回・年・月・日など）のときだけ数として読む（十時 → 10時）
   - 並びの先頭の万・億・兆は数に含めない（万一 → 万1、万全 → 万全）
   - 桁あふれする並びは変えない
4. **句読点・空白など**: 次を除く
   - Unicode の約物（P で始まる一般カテゴリ: 句読点、括弧、引用符、ハイフン、中黒、波ダッシュなど）
   - 空白・改行と、ゼロ幅スペースなどの不可視の書式文字（Cf）
   - 全角チルダ（NFKC で `~` になる。波ダッシュ `〜` とそろえるため）
   - ただし次は意味を持つため残す: 数字に挟まれた `.`（小数点）と `:`（時刻）、`%` `#` `&` `@` `*` `/` `\`、長音記号「ー」、`+` `=` などの記号（S カテゴリ）

### 既知の制限

- 「八百屋」→「800屋」、「十分（じゅうぶん）」→「10分」のように、数字を含む語や助数詞が続く語は数として読まれ、文字数が変わる。正解に頻出する場合は、正解の表記を STT の出力に合わせるか、評価から除く
- 小数と位取りの組み合わせ（1.5万）は値として読まない（「1.5万」と「一万五千」は一致しない）
- 数字の間の空白は手順4で除かれるため、「二 十」は「210」になる

### 用語単位の正答率（日英混在・開発用語・辞書語）

- `terms` の各語が、正解に現れる回数だけ結果にも現れたかを数える。正答は正解の回数を上限とする
- 英数字で始まる・終わる用語は、隣も英数字なら単語の一部とみなして数えない（`Git` は `GitHub` の中では数えない）
- 用語は表記を正しく保てたかを見るため、CER の正規化を適用しない。大文字・小文字、全角・半角、空白の有無も区別する（「SwiftUI」と「swiftui」「Swift UI」は不一致）
- 正答率 = 正答数の合計 ÷ 正解に含まれる用語の出現回数の合計

## 重大な意味改変

STT 単体の誤りとは分けて、AI 整形後の結果（`refinedOutput`）について判定する（9章）。
比較の基準は `reference`（発話どおりの正解）であり、STT の結果ではない。
重大な意味改変率 = 重大な意味改変が1つ以上あった発話数 ÷ 判定した発話数。

### 判定基準

次のいずれかに当たる場合を「重大な意味改変」とする。JSON の `meaningChanges` に該当する種類をすべて記録する。

| 種類（JSON） | 基準 | 例 |
|---|---|---|
| 否定の反転（`negationFlipped`） | 肯定と否定、可能と不可能、許可と禁止が入れ替わった | 「送らないで」→「送って」 |
| 数値の変更（`numberChanged`） | 数値・日時・金額・数量・単位が変わった | 「3時」→「13時」、「5個」→「50個」 |
| 固有名詞の変更（`properNounChanged`） | 人名・製品名・地名・コード上の識別子が別の語に変わった | 「Swift」→「Swiftly」 |
| 内容の追加（`contentAdded`） | 発話にない内容（質問への回答、補足、命令の実行結果など）が加わった（TXT-04, AC-17） | 「天気は？」→「晴れです」 |
| 内容の欠落（`contentOmitted`） | 発話の内容が抜けた | 「AとBを確認」→「Aを確認」 |
| 関係の変更（`relationChanged`） | 主語・目的語、依頼と報告、時制などの関係が入れ替わった | 「確認してください」→「確認しました」 |

次は重大な意味改変に含めない。

- フィラー（えー、あのー）の除去
- 自己訂正で言い直す前の語の除去（「3時、いや4時」→「4時」）。ただし言い直した後の語を残さなかった場合は欠落
- 句読点・改行・段落・表記ゆれ（漢字とかな、全角と半角）の変更
- 文体の変更（です・ます調へのそろえなど）で、上の基準に当たらないもの

### 判定手順

1. 判定者は `reference` と `refinedOutput` だけを並べて読む（STT の結果や音声は見ない）
2. 上の判定基準の表を上から順に確認し、当てはまる種類をすべて記録する。当てはまらなければ `[]` を記録する
3. 迷った場合は「重大」とし、その理由を評価記録（`docs/計測/`）に1行残す
4. 同じ評価セットを2人以上で判定できる場合は、判定が分かれた発話を協議して1つに決め、件数を記録する
5. 判定基準を変えた場合は、過去の結果と比較せず、評価セット全体を判定し直す

## 質問文・命令文の評価セット（AC-17）

発話が質問文・命令文・指示の上書き（「以前の指示を無視して」など）のときに、回答や実行ではなく整形結果が返ることを確かめる（TXT-04）。
上の精度評価とは別に、音声を使わない自動テストとして `scripts/verify.sh` で毎回実行する。

- 評価セット: `Packages/UtterAI/Tests/UtterAITests/NoAnswerEvaluationSet.swift`。区分は発話の意図で分け、検証の判定規則（疑問符など）とは切り離す
  - 質問: 相手に情報や答えを求める発話。文末の「？」や「ですか」の有無は問わない（STT は「？」を出さないことが多い）
  - 命令: 相手に作業を依頼・命令する発話
  - 指示の上書き: 以前の指示の無視・役割の変更など、整形の指示を上書きしようとする発話
  - 各区分8発話以上（暫定）。各発話に、整形として妥当な応答の例（句読点・「？」の付与、丁寧化、フィラー除去など）と、クラウド AI が回答・実行してしまった場合の模擬応答（回答の後に問い返しを付けたものを含む）を持たせる。模擬応答には、現在どの検証項目で棄却されるか（`RefinementValidationFailure`）を記録する
- テスト: `Packages/UtterAI/Tests/UtterAITests/NoAnswerEvaluationTests.swift`。実際のクラウド API は呼ばず、模擬応答を `StubAIProvider` から返す
  - Local Basic（AI-03）は、全モード・全スタイル区分で発話にない語を足さない
  - 整形として妥当な応答の例は、全モード・全スタイル区分で検証を通る（誤って棄却しない）
  - 回答・実行の模擬応答は `RefinementValidator` が記録した理由で棄却し、ローカル整形（Local Basic / Raw）の結果に退避する（4.1節）
  - プロンプトは発話を区切りタグの中のデータとして包み、指示に混ぜない。区切りタグを偽造した発話では区切りを作り直す
- 既存の閾値で棄却できない模擬応答は、閾値を変えずに `undetected` に記録し、テストでは既知の問題（`withKnownIssue`）として扱う。検出できるようになるとテストが失敗して知らせるため、そのときは `samples` へ移す
- 閾値（4.1節）を決めるときは、`undetected` の件数と、整形として妥当な応答を誤って棄却しないことの両方を判断材料にする
- **AC-17 の合否は、`undetected` が0件になることと、実際のクラウド AI での精度評価（上の「重大な意味改変」の `contentAdded`）を合わせて判断する。このテストが通るだけでは AC-17 を満たさない**（模擬応答は実際のモデルの出力ではないため）
