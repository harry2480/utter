# docs テンプレート化計画書

## 1. 実施フェーズ

### Phase 1: 対象ドキュメントの分類
- docs 内の資料を「そのまま残す」「テンプレート化する」「アーカイブする」に分類する
- 現状のファイル一覧を確定する（完了）

### Phase 2: 汎用ドキュメントの整備
- 汎用的な資料はそのままテンプレートとして残す
- 固有の名前・パス・データ構造を含む資料は、プレースホルダー化して再利用可能にする
- 変更後に文脈とコード例を目視確認する

### Phase 3: プロジェクト固有資料の整理
- 他プロジェクトで再利用しにくい資料を特定する
- 必要に応じて `docs/archive/` に移動し、現行のガイド類と分離する

### Phase 4: 構成確認と提出
- 整理後の docs 構成と参照を確認する
- 差分をレビューし、変更を PR で提出する

## 2. 詳細実施計画

### 2.1 そのまま残す資料

以下は汎用的で、プロジェクト固有の情報を含まないため、そのまま残す。

| ファイル | 内容 |
|---|---|
| `architecture.md` | DDD 4層設計規約 |
| `frontend.md` | Next.js、shadcn/ui、Tailwind の規約 |
| `infrastructure.md` | pnpm monorepo、Vercel、Supabase、Prisma の構成 |
| `quality.md` | Vitest、TypeScript、dependency-cruiser による品質規約 |
| `20260220_1530_スタイルガイド.md` | Tailwind の `dvh` ルール |

### 2.2 テンプレート化する資料

主にプレースホルダー化とコード例の汎用化を行う。

| ファイル | 変更内容 |
|---|---|
| `20260301_0700_開発用UIプレビュー環境.md` | `features/bills/`、`BillCard` などを `features/<feature>/`、`<YourComponent>` に置き換える |
| `20260219_1000_テストガイドライン.md` | プロジェクト固有の説明を除き、関数名やパスを汎用化する |
| `repository-layer.md` | `@mirai-gikai/supabase`、`bills` などをプロジェクト名・エンティティのプレースホルダーに置き換える |
| `20260407_1800_adminGoogleログイン設定手順.md` | アプリ名、ポート、ロール名を `<project-name>`、`<PORT>` などに置き換える |

置換後は、用語の整合性、コード例、手順が特定プロジェクトに依存せず理解できることを確認する。単純な一括置換だけで完了とせず、各資料を目視レビューする。

### 2.3 アーカイブする資料

- 対象は、他プロジェクトで再利用しにくいプロジェクト固有資料（現時点の想定は23件）
- `docs/archive/` に移動し、通常のガイド・テンプレートと分ける
- 対象一覧を移動前に確定し、件数と移動後の配置を確認する
- 例: 20250904〜20251221 のみらい議会固有仕様、特定時点のスナップショット資料

### 2.4 整理後の docs 構成

```text
docs/
├── architecture.md
├── frontend.md
├── infrastructure.md
├── quality.md
├── repository-layer.md
├── 20260219_1000_テストガイドライン.md
├── 20260220_1530_スタイルガイド.md
├── 20260301_0700_開発用UIプレビュー環境.md
├── 20260407_1800_adminGoogleログイン設定手順.md
└── archive/
    └── プロジェクト固有資料
```

### 2.5 検証

- 整理後のファイル一覧が上記の構成と一致する
- プロジェクト固有の名前、パス、データ構造がテンプレートに残っていない
- アーカイブ対象が漏れずに移動され、現行資料からの参照が壊れていない
- Markdown の見出し、表、コードフェンス、リンクを確認する
- `git diff --check` を実行する

## 3. 作業フローと目安

1. 対象ファイルの分類を確定する（完了）
2. テンプレート化する資料を修正し、目視レビューする
3. アーカイブ対象を `docs/archive/` に移動する
4. docs 全体の構成と参照を検証する
5. 差分を PR で提出し、レビュー指摘に対応する

| ステップ | 工数目安 |
|---|---:|
| 現状調査 | 0.5日 |
| 修正設計 | 0.5日 |
| テンプレート化作業（4ファイル） | 1.0日 |
| アーカイブ作業 | 0.5日 |
| PR 作成・レビュー対応 | 0.5日 |

## 4. 完了条件

- 汎用資料がテンプレートとして再利用できる
- プロジェクト固有資料が `docs/archive/` に整理されている
- docs の最終構成と参照に不整合がない
- Markdown の差分チェックが成功している
- 変更が PR でレビュー可能な状態になっている
