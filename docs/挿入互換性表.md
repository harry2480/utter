# 挿入互換性表（macOS）

utter（macOS 版）が主要なアプリの入力欄へ文字列を挿入するときに、どの経路を使い、挿入を確かめられるか、Undo とクリップボードがどうなるかをアプリごとにまとめた表である（AC-20、INS-02、INS-05、INS-07）。

- 利用者向けには「このアプリでは自動挿入できるか、取り消せるか、何に気をつければよいか」を公開する
- 開発者向けには、アプリ別の既定経路（`InsertionPolicy` に渡す `AppInsertionProfile`）の根拠にする

> **現状:** Phase 0 の実機検証（[Phase0検証-Accessibility挿入成功率.md](Phase0検証-Accessibility挿入成功率.md)、#41）は未実施のため、結果欄はすべて「未確認」である。計測していない値を推測で書かない。

## 1. 対象と範囲

- 対象は macOS 版のみ。iOS のキーボード拡張（`UITextDocumentProxy` 経由の挿入）は [Phasei3検証-実機継続利用.md](Phasei3検証-実機継続利用.md) の「主要アプリでのキーボード互換性」で記録する
- 対象アプリは Phase 0 手順書の「アプリ・入力欄別テスト」の表に合わせる（2章）。アプリを追加するときは 6章の手順に従う
- パスワード欄などのセキュア入力欄は互換性の対象ではない。録音・挿入を抑止するのが正しい動作であり（7章、AC-12）、抑止されたことを Phase 0 手順書の異常系テストで確認する
- Realtime Direct（Phase 4、AC-15）の対応可否はこの表では扱わない。必要になったときに列を追加する

## 3. 列の定義と書き方

| 列 | 書くこと | 値の例 |
|---|---|---|
| アプリ | アプリの表示名 | Safari |
| bundle ID | `InsertionPolicy` の `profiles` のキーになる識別子 | `com.apple.Safari` |
| 版 | 確認したアプリのバージョン（アプリの「〜について」の表記） | 26.0 |
| 入力欄の種類 | 確認した入力欄。Web ページなら要素の種類も書く | `<input type="text">`、contenteditable、メッセージ欄 |
| 既定経路 | utter がこの入力欄で最初に使う経路。挿入できない場合は「プレビュー退避」 | AX、Pasteboard、CGEvent、プレビュー退避 |
| 代替経路 | 既定経路が「挿入されていないことが確かな失敗」（送信前の失敗、または読み戻しで変化がないと確かめた場合）で終わったときに試す経路を順に書く。成功不明のときは試さない。なければ「なし」 | Pasteboard → CGEvent、なし |
| 成功確認（読み戻し） | 挿入後の値を読み戻して確かめられるか（INS-05） | 可、不可（成功不明として扱う）、一部可（条件を既知の制限に書く） |
| Undo | アプリ標準の取り消し（⌘Z）で挿入全体を取り消せるか（INS-07） | 1回で全体を取消、複数回必要、一部だけ取消、取消不可 |
| クリップボード復元 | Pasteboard 経路を使ったとき、元のクリップボードが種類・内容とも戻るか、クリップボード管理アプリの履歴に残らないか（INS-04、INS-06） | 復元可・履歴なし、復元可・履歴あり、復元不可、対象外（Pasteboard を使わない） |
| 判定 | 4章の基準による判定 | 成功、条件付き、非対応、未確認 |
| 既知の制限 | 利用者が知っておくべき制限。条件付き・非対応の理由は必ず書く | 「改行を含む文字列は自動挿入せずプレビューに退避する」 |
| 確認日 | 実機で確認した日 | 2026-11-01 |
| 確認者 | 確認した人の GitHub ユーザー名 | `@example` |
| macOS 版 | 確認した Mac の macOS のバージョンとビルド番号 | 26.1（25B78） |

経路の表記は、コードの `InsertionRoute` と次のように対応する。

| 表の表記 | `InsertionRoute` | 内容 |
|---|---|---|
| AX | `.accessibility` | Accessibility API による直接挿入 |
| Pasteboard | `.pasteboard` | 許可済みの Pasteboard 経由の貼り付け |
| CGEvent | `.keyEvents` | 許可済みの CGEvent によるキー入力 |
| プレビュー退避 | （経路なし） | 自動挿入せず、コピー可能なプレビューを表示する |

Enter（Return キー）を自動で送る経路はない（INS-03、AC-08）。どの行でも、挿入によってコマンドやメッセージが送信されないことを確認する。

## 4. 判定基準

判定は、その行の **既定経路と代替経路で実際に起きること** で決める。経路ごとの試行回数・成功数は Phase 0 手順書の記録テンプレートに残し、この表には結論だけを書く。

| 判定 | 定義 |
|---|---|
| 成功 | 既定経路で、Phase 0 手順書の試行（各20回以上）がすべて成功した。成功は読み戻しで一致を確かめたもの（読み戻せない場合は目視で完全一致）。加えて、Undo 1回で挿入全体を取り消せる、Pasteboard を使う場合はクリップボードを復元でき履歴に残らない、二重挿入・Enter の送信・別の入力欄への挿入が0件 |
| 条件付き | 自動挿入はできるが、成功の条件の一部を満たさない。ただし誤った挿入（二重挿入・Enter の送信・別の入力欄への挿入・一部欠落したままの確定）は0件で、満たせない場合は安全側（成功不明として再試行しない、プレビュー退避）に倒れる。例: 読み戻せず成功不明になる、Undo が複数回必要、改行を含む文字列はプレビュー退避になる。満たさない条件を既知の制限に書く |
| 非対応 | 自動挿入できる経路がない、または誤った挿入を既定経路・代替経路のどちらでも防げない。既定経路を「プレビュー退避」にし、理由を既知の制限に書く |
| 未確認 | 実機で確認していない、または確認した版から 5章の再確認の条件に当たる変更があった |

- 読み戻しができないこと自体は非対応の理由にしない。成功不明として扱い、無条件に再試行しない（INS-03、INS-05）
- 誤った挿入が1件でもあった経路は、その入力欄の既定経路・代替経路にしない
- AX は、読み戻しで成功を確認できる入力欄でだけ既定経路にする。読み戻せない入力欄では Pasteboard 経路またはプレビュー退避を既定にする（要件定義 11章）
- 迷ったときは安全側の判定（成功より条件付き、条件付きより非対応）にする

## 5. 記入手順

### 初回（Phase 0）

1. [Phase0検証-Accessibility挿入成功率.md](Phase0検証-Accessibility挿入成功率.md) の手順で、2章の各行の入力欄について経路ごとに試行し、手順書の記録テンプレートに試行数・成功数・読み戻し・Undo・失敗理由を書く。異常系テスト（フォーカス移動・ウィンドウ消失・パスワード欄・Terminal の改行・二重挿入）とクリップボード復元テストも行う
2. 記録から、各行の既定経路と代替経路を決める。誤った挿入があった経路を外し、残りのうち成功した経路を `InsertionPolicy` の既定の順（AX → Pasteboard → CGEvent）で並べ、最初のものを既定経路にする。ただし AX は読み戻しで成功を確認できた場合だけ既定経路にできる（4章、要件定義 11章）
3. 4章の基準で判定し、この表の行を埋める。条件付き・非対応は既知の制限を必ず書く
4. 確認日・確認者・macOS 版を書く
5. 既定経路が既定の順と違う行、またはターミナル系のアプリの行は、`AppInsertionProfile` の設定（`routes`、`isTerminal`）に反映する。反映はアプリターゲットの実装（Phase 1）で行う

### 再確認

次のどれかに当たったら、該当する行の判定を「未確認」に戻し、1〜4を行い直す。

- macOS のメジャーバージョン・マイナーバージョンを上げた
- 対象アプリのメジャーバージョンが上がった、またはリリースノートに入力欄・Accessibility の変更がある
- utter の挿入の経路・読み戻し・クリップボード復元の実装を変えた
- 利用者から、その行と異なる挙動の報告があった

リリースごとに、各行の確認日と版が直近の macOS・アプリに対して古くないかを見直す（AC-19）。

### 記録の注意

- 挿入には検証用のダミー文字列だけを使う。実在の個人情報・仕事の文章・パスワードを使わない（品質チェック・テスト規約）
- スクリーンショットや画面収録はリポジトリにコミットしない。他のアプリの内容や通知が写り込むため、判定と既知の制限だけを書く
- 確認者は GitHub ユーザー名で書き、実名・メールアドレスを書かない

## 6. アプリの追加

1. 追加の理由（利用者からの要望、CTX-01 の対応表に含まれるアプリなど）を Issue に書く
2. 2章の表に行を追加し、結果欄を「未確認」にする
3. Phase 0 手順書の「アプリ・入力欄別テスト」と同じ手順・試行回数で確認し、5章の手順で埋める

ターミナル系のアプリ（シェルを操作するアプリ）は、改行が Enter として実行される危険があるため、判定にかかわらず `isTerminal` を有効にする前提で行を作る（INS-03、AC-08）。

## 8. コードとの対応

| 本書 | コード（`Packages/UtterCore`） |
|---|---|
| 1行（アプリ × 入力欄） | `AppInsertionProfile`（アプリ単位。入力欄ごとの区別はない） |
| 既定経路・代替経路 | `AppInsertionProfile.routes`。未設定なら `InsertionPolicy.defaultRoutes`（AX → Pasteboard → CGEvent） |
| ターミナル系のアプリ | `AppInsertionProfile.isTerminal`。改行を含む文字列はプレビューへ退避する（`InsertionPreviewReason.multilineInTerminal`） |
| 成功確認（読み戻し） | `InsertionReadBack` と `InsertionResult.classify`。読み戻せない場合は `unconfirmed`（成功不明）になり再試行しない |
| クリップボード復元 | `ClipboardRestorePolicy`（changeCount が書き込み直後と同じときだけ復元する） |
| プレビュー退避 | `InsertionNextStep.showPreview` |

コードの `AppInsertionProfile` はアプリ単位のため、同じアプリで入力欄によって既定経路が違う結果になった場合は、そのまま反映できない。その場合は、そのアプリの入力欄すべてで安全な経路（誤った挿入がない経路）だけを `routes` に残す。それでも主要な入力欄で使える経路がなくなる場合は、入力欄単位の設定を追加するかを Issue で判断する。
