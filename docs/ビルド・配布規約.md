## 依存関係

- 依存は各 Package の `Package.swift` に記述し、`Package.resolved` をコミットしてバージョンを固定する
- macOS アプリ（`Apps/macOS/project.yml` と `Apps/macOS/Specs/`）が直接使う依存（Sparkle, `Specs/Sparkle.yml`）は `exactVersion` で固定し、`Apps/macOS/Package.resolved` をコミットする。Xcode のプロジェクトでは `Package.resolved` が生成物（gitignore 済みの `Utter.xcodeproj`）の中に置かれるため、`xcodegen generate` の `postGenCommand`（`scripts/install-mac-package-resolved.sh`）が生成のたびに中へ写す。`scripts/verify.sh`・`scripts/build-local.sh`・`scripts/release-macos.sh` は `-disableAutomaticPackageResolution` で、写した `Package.resolved` のとおりに取得する
  - 版を変えるとき：`Specs/Sparkle.yml` の `exactVersion` を直す → `xcodegen generate` → `xcodebuild -project Apps/macOS/Utter.xcodeproj -scheme UtterMac -resolvePackageDependencies`（`-disableAutomaticPackageResolution` を付けない）→ `scripts/install-mac-package-resolved.sh --update` で `Apps/macOS/Package.resolved` に書き戻してコミットする。Dependabot は `Packages/*` だけを見るため、Sparkle の更新は人が確認する
- 依存を追加する前にライセンスを確認する（Apache-2.0 と両立するもの）。モデル重みのライセンスも別途確認する。確認結果は [ライセンス・依存関係.md](ライセンス・依存関係.md) に出典と確認日つきで記録する
- 依存の更新は Dependabot（`swift` エコシステム）が PR を作成する。自動マージはせず、人がレビューしてマージする

## 署名と識別子

Accessibility 等の権限はコード署名に紐づくため、署名が変わると再許可が必要になる。

- Team ID・Bundle ID・App Group ID はリポジトリに固定せず、`Config/Local.xcconfig`（gitignore 済み）で上書きする。既定値は `Config/Base.xcconfig`（署名なしビルド用のダミー）、雛形は `Config/Local.xcconfig.example`
- 自前ビルド利用者向けに、固定の開発用署名でビルドする手順を下の「[自前ビルド（固定の開発用署名）](#自前ビルド固定の開発用署名ac-13)」に記載する（README から参照）。Ad Hoc 署名は再ビルドのたびに権限が外れるため使わない（方式案は [ライセンス・依存関係.md](ライセンス・依存関係.md) 4章）
- macOS 公式バイナリは Developer ID 署名＋公証（下の「[リリース](#リリースdeveloper-id-署名公証github-releases)」）。App Sandbox は原則使わない（他アプリへの AX 操作のため。`scripts/check-release-config.sh` が有効になっていないことを確かめる）
- Release 構成は Hardened Runtime を有効にする（`Apps/macOS/project.yml` の `configs.Release`、公証の必須条件）。Entitlement は `Apps/macOS/UtterMac.entitlements` に、今ある機能が使うものだけを置く。Hardened Runtime ではマイクに `com.apple.security.device.audio-input` が要るため、録音を実装する PR で追加する（用途説明だけあって Entitlement がないと `scripts/check-release-config.sh` が失敗する）
- iOS は iOS Development 署名で本人端末にインストールする。無料 Personal Team は約7日で失効するため再インストールが必要。App Group が無料署名で使えるかは Phase i0 で検証する
- 証明書・プロビジョニングプロファイル・API キー（`*.p12` / `*.p8` 等、gitignore 済み）はコミットしない。CI の署名はリリース用ワークフローだけが Environment `release` の secrets を使い、PR からのワークフローに渡さない

## ビルド手順

Xcode プロジェクトは xcodegen で `project.yml` から生成する。生成物（`*.xcodeproj`）はコミットしない（.gitignore。`project.yml` が正）。
コマンドはリポジトリのルートで実行する。

複数の PR が同じ行に追記して衝突しないよう、macOS アプリは次のように分ける。

- パッケージとアプリからの依存、機能ごとのビルド設定は `Apps/macOS/Specs/` に1件1ファイルで置き、`Apps/macOS/project.yml` の `include` に1エントリ足す（`relativePaths: false` で、パスは `project.yml` からの相対パス）
- 画面（`Scene`）とメニューの項目は `Apps/macOS/Sources/<機能>/` に置き、`Sources/UtterApp.swift` と `Sources/AppMenu.swift` には1機能1行で並べるだけにする
- 新しいエントリ・行は、末尾にまとめて足さず、関係するものの近くに足す

| ターゲット | 定義 | スキーム | 成果物 |
|---|---|---|---|
| macOS アプリ（メニューバー常駐、Dock に出さない `LSUIElement`） | `Apps/macOS/project.yml` | `UtterMac` | `utter.app`（Bundle ID は `<UTTER_BUNDLE_ID_PREFIX>.mac`） |

```sh
# 1. プロジェクトを生成（project.yml を変えたら毎回）
xcodegen generate --spec Apps/macOS/project.yml

# 2a. 署名なしでビルド（scripts/verify.sh・CI と同じ条件）
xcodebuild -project Apps/macOS/Utter.xcodeproj -scheme UtterMac -configuration Debug \
  -destination 'generic/platform=macOS' CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=NO build

# 2b. 開発用署名でビルドする（自前ビルド。下の「自前ビルド」の手順で Local.xcconfig を用意してから）
scripts/build-local.sh            # Release 構成（Hardened Runtime）。-c Debug で Debug 構成
# または Xcode から実行する
open Apps/macOS/Utter.xcodeproj   # スキーム UtterMac で Run
```

- `xcode-select -p` が Command Line Tools を指していると xcodebuild を実行できない。`sudo xcode-select -s /Applications/Xcode.app` で切り替えるか、`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` を付けて実行する
- 署名を固定するため、`Local.xcconfig` の Team ID・Bundle ID は一度決めたら変えない（変えると Accessibility 等の権限の再許可が必要になる）
- Packages はローカルパッケージとして参照する（現在は UtterCore のみ。使う Package は機能を結線する PR で追加する）
- 権限の用途説明（`NSMicrophoneUsageDescription` など）と Entitlement は、その権限を使う機能を実装する PR で追加する。未使用の権限は要求しない（PERM-01）

### 自前ビルド（固定の開発用署名、AC-13）

maintainer の証明書・API キーなどの秘密情報は使わない。各自の Apple ID の開発用署名（Apple Development、無料の Personal Team でよい）でビルドする（[ライセンス・依存関係.md](ライセンス・依存関係.md) 4.2 の案 L1）。

1. Xcode > Settings > Accounts に自分の Apple ID を追加し、Team ID（英大文字・数字10桁）を確認する。キーチェーンアクセスの `Apple Development: …` 証明書の「部署（OU）」にも Team ID が入っている
2. `cp Config/Local.xcconfig.example Config/Local.xcconfig` で雛形をコピーし、`DEVELOPMENT_TEAM` に Team ID、`UTTER_BUNDLE_ID_PREFIX` に他人と重ならない逆ドメイン（例 `io.github.<GitHub ユーザー名>.utter`）を書く
3. `scripts/build-local.sh` を実行する。xcodegen でプロジェクトを生成し、自動署名（`CODE_SIGN_IDENTITY` は `Apple Development`、`-allowProvisioningUpdates`）で Release 構成をビルドする。開発用証明書がなければ Xcode が作る
4. 成果物は `build/local/DerivedData/Build/Products/Release/utter.app`。スクリプトは署名の発行元と designated requirement（DR）を表示する。Ad Hoc 署名（Team ID が Xcode のアカウントにない場合など）になっていれば失敗する

**許可（TCC）が再ビルドで外れないための決まり**：Accessibility・マイク等の許可は DR に紐づく。Ad Hoc 署名の DR はビルドごとに変わるため、毎回再許可が必要になる。

- `Local.xcconfig` の `DEVELOPMENT_TEAM` と `UTTER_BUNDLE_ID_PREFIX` は一度決めたら変えない（Bundle ID は DR に含まれる）
- 同じ Apple Development 証明書で署名し続ける。DR は証明書の CN（`Apple Development: <名前> (<ID>)`）と発行元で決まる（TN3127）。`scripts/build-local.sh` が表示する DR が前回と同じなら、許可は引き継がれる
- 証明書を作り直した・別の Mac でビルドした・公式バイナリ（Developer ID）に切り替えた場合は DR が変わり、システム設定 > プライバシーとセキュリティ で許可し直す。古い項目は `-` で消してから追加し直す（`tccutil reset All <Bundle ID>` でもよい）
- 確認手順（#47 の 4.2 の確認手順と同じ）：同じ設定で2回ビルドし、`codesign -d -r- <utter.app>` の DR が同じこと、1回目で許可した権限を2回目で再要求されないことを確かめる。結果はこの節に記録する（未実施）

秘密情報を使わないビルドは、ほかに署名なしのビルド（上の 2a、`scripts/verify.sh`・CI と同じ）がある。署名なしの成果物は権限の確認には使えない（起動できても許可を保持できない）。

## CI

`.github/workflows/ci.yml`

| job | ランナー | 内容 |
|---|---|---|
| 検証（`verify`） | `macos-26` | `scripts/verify.sh`（swift format lint、Package の build/test、アプリの署名なし xcodebuild、Release の署名設定の検査、shellcheck、actionlint）。shellcheck・xcodegen・actionlint は brew で導入する |
| CI ステータス確認（`ci-status`） | `ubuntu-latest` | `verify` の結果を集約。branch protection の required check にする |
| カバレッジ計測（`coverage.yml`） | `macos-26` | `scripts/coverage.sh` の lcov を Codecov にアップロード。required check にはしない |
| 署名・公証・リリース（`release.yml`） | `macos-26` | `v*` タグの push か手動実行でだけ起動する。下の「リリース」 |

- アプリターゲットは `scripts/verify.sh` で署名なし（`CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=NO`）の `xcodebuild build` を行う。新しいターゲットを作ったら追加し、テスト・ターゲットを作ったら `xcodebuild test` も追加する
- 実機・権限ダイアログ・マイクが必要なテストは CI で実行しない。手順書と記録で担保する
- Codecov のアップロードトークンは Actions secrets の `CODECOV_TOKEN` に設定する。アップロード失敗では CI を落とさない
- ランナーの macOS / Xcode バージョンを変えたときは、ローカルとの差異を README に記録する

### リリース（Developer ID 署名・公証・GitHub Releases）

**Phase 0 #47（署名方式の確定）の判定待ちの先行実装**（[ライセンス・依存関係.md](ライセンス・依存関係.md) D-7 の案 N1）。Secrets を登録するまでは最初のステップで失敗し、何も作らない。#47 で N2（手元で署名・公証）に決まった場合は `.github/workflows/release.yml` を削除し、`scripts/release-macos.sh` を手元で実行する。

| 項目 | 内容 |
|---|---|
| ワークフロー | `.github/workflows/release.yml`。起動は `v*` タグの push か、Actions 画面からの手動実行（Use workflow from で既存のタグを選ぶ。ブランチからは進まない）だけ。`pull_request` / `pull_request_target` では起動しない |
| 処理 | Secrets の確認 → タグの形式の確認 → 一時キーチェーンに Developer ID 証明書を取り込む → `scripts/release-macos.sh`（Team ID の Developer ID 証明書がちょうど1つあることを確認 → xcodegen → Release 構成の検査 → `xcodebuild archive`（その証明書で手動署名）→ `-exportArchive`（`developer-id`）→ 署名の確認（Developer ID・Hardened Runtime・secure timestamp・get-task-allow がない・マイクを使うなら audio-input）→ `notarytool submit --wait` → `stapler staple` → zip と dmg（dmg も署名・公証・staple）→ `SHA256SUMS.txt`）→ GitHub Release を**下書き**で作成して添付 → 一時キーチェーンと API キーを削除 |
| 版 | タグ `v0.1.0` → `CFBundleShortVersionString` 0.1.0。プレリリース（`v0.1.0-beta.1`）は接尾辞を除いた値にし、Release をプレリリースにする。`CFBundleVersion` は Actions の実行番号 |
| 公開 | 下書きの本文に計測結果と既知の制限（AC-19）を書いてから、人が公開する。同じタグの Release（下書きを含む）が既にあると失敗するので、作り直すときは先に削除する |
| 秘密情報の扱い | `set -x` を使わない。キーチェーンのパスワードはジョブごとに生成してマスクする。`.p12` と `.p8` は `$RUNNER_TEMP` に置き、終わったら削除する。チェックアウトは `persist-credentials: false` |

Environment `release` の設定（maintainer が GitHub の Settings > Environments で行う）：

- 承認者（Required reviewers）を設定する。承認されるまでジョブは Environment の secrets を読めない
- Deployment branches and tags を「Selected」にし、タグ `v*` だけを許可する

| 種類 | 名前 | 内容 |
|---|---|---|
| secret | `MACOS_DEVELOPER_ID_P12_BASE64` | Developer ID Application の証明書と秘密鍵を書き出した `.p12` を `base64 -i <file>.p12` した値 |
| secret | `MACOS_DEVELOPER_ID_P12_PASSWORD` | `.p12` を書き出したときのパスワード |
| secret | `APPLE_TEAM_ID` | Developer ID 証明書の Team ID |
| secret | `ASC_API_KEY_P8_BASE64` | App Store Connect API キー（Team キー、役割は Developer）の `.p8` を `base64 -i <file>.p8` した値 |
| secret | `ASC_API_KEY_ID` | API キーの Key ID |
| secret | `ASC_API_ISSUER_ID` | API キーの Issuer ID |
| variable | `UTTER_BUNDLE_ID_PREFIX` | 公式バイナリの Bundle ID の接頭辞（macOS アプリは `<接頭辞>.mac`）。一度決めたら変えない（変えると利用者の許可が外れる） |
| secret | `SPARKLE_ED_PRIVATE_KEY` | 任意。自動更新の EdDSA 秘密鍵（`generate_keys -x <file>` で書き出したファイルの中身）。下の「自動更新」 |
| variable | `SPARKLE_PUBLIC_ED_KEY` | 任意。自動更新の EdDSA 公開鍵（`generate_keys` が表示する Base64）。`SPARKLE_ED_PRIVATE_KEY` と両方登録したときだけ自動更新が有効になり、片方だけだと最初のステップで失敗する |

手元（maintainer の Mac）で同じ処理をするときは、Developer ID 証明書をログインキーチェーンに入れ、`scripts/release-macos.sh` の先頭に書いた環境変数を渡して実行する（`UTTER_KEYCHAIN_PATH` は省略できる）。

### 自動更新（Sparkle 2）

**Phase 0 #47（依存のライセンス確定）の判定待ちの先行実装で、既定で無効**（#60）。appcast の URL と EdDSA 公開鍵がビルド設定で与えられたときだけ、アプリは Sparkle を起動する。与えなければ Sparkle のオブジェクトを作らず、更新の確認で通信しない。不採用になったら、`Apps/macOS/Specs/Sparkle.yml`（Sparkle の依存・ライセンス表示・Info.plist の指定）と `Apps/macOS/project.yml` のその include・`Apps/macOS/Sources/Update/`・メニューの項目・`Apps/macOS/Info.plist` の `SU*` キー・`Apps/macOS/Package.resolved`・リリースの Sparkle 部分・`UtterCore` の `SoftwareUpdateConfiguration` を外す。

| 項目 | 内容 |
|---|---|
| 有効にする条件 | ビルド設定 `UTTER_SPARKLE_FEED_URL`（https）と `UTTER_SPARKLE_PUBLIC_ED_KEY`（Base64 の 32 バイト）が両方あること。`Config/Base.xcconfig` では空。判定は `UtterCore` の `SoftwareUpdateConfiguration`。片方だけ・形式の誤りでも無効にし、理由だけを OSLog に残す |
| 確認の間隔 | 1 週間（`SUScheduledCheckInterval` = 604800 秒）。要件は「低頻度」で値の定めがないため**仮置き** |
| 自動確認の可否 | Sparkle が 2 回目の起動時に利用者に確かめる（`SUEnableAutomaticChecks` を Info.plist に置かない）。メニューバーの「アップデートを自動で確認」で切り替えられる。設定画面ができたらそちらへ移す |
| 送る情報 | システムプロファイル（OS 版・機種など）を送らない（`SUEnableSystemProfiling` = NO、`sendsSystemProfile` = false、appcast の問い合わせにパラメータを付けない） |
| インストール | 自動ダウンロード・自動インストールは選べない（`SUAllowsAutomaticUpdates` = NO）。入れる前に必ず利用者に確かめる |
| 公式バイナリ | リリース用ワークフローで `SPARKLE_ED_PRIVATE_KEY` と `SPARKLE_PUBLIC_ED_KEY` を両方登録したときだけ有効。appcast の URL は `https://github.com/<リポジトリ>/releases/latest/download/appcast.xml`（最新の公開済み Release に添付したもの。下書き・プレリリースは配らない）。`scripts/release-macos.sh` が公開鍵の形式（Base64 の 32 バイト）を確かめ、zip を Sparkle の `sign_update` で EdDSA 署名し、その署名を公開鍵で検証してから（鍵ペアの食い違いで、配った版が更新を受け付けなくなるのを防ぐ）、1 項目の `appcast.xml` を作って Release に添付する |
| 自前ビルドで試す | `Config/Local.xcconfig` に URL と公開鍵を書く（書き方は `Config/Local.xcconfig.example`。xcconfig では `//` がコメントになるので `https:/$()/…` と書く） |

`scripts/verify.sh` は、URL と公開鍵を空にしてビルドし（`Local.xcconfig` に書いていても）、 Info.plist の `SUFeedURL`・`SUPublicEDKey` が空であることと、上の間隔・送る情報・インストールの設定を確かめる。

鍵の作成（maintainer、初回だけ）：Sparkle の `generate_keys`（`build/DerivedData/SourcePackages/artifacts/sparkle/Sparkle/bin/` など、Package の取得先にある）で鍵を作り、表示された公開鍵を variable に、`generate_keys -x <file>` で書き出した秘密鍵を secret に登録する。書き出したファイルは登録後に削除する。秘密鍵を失うと、既に配った版へ更新を届けられなくなる（Sparkle の鍵の差し替え手順が必要）。

- STT モデルはバイナリに同梱せず、初回にユーザー操作で取得する（取得元・サイズを明示し、取得後に完全性を検証, PERM-03）
- リリースごとに性能・精度の計測結果を記録し、目標未達の項目は既知の制限として公開する（AC-19）
