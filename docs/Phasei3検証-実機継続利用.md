# Phase i3 検証: 互換性・性能・プライバシー・実機継続利用（#63）

## 目的

iOS 個人利用版を本人の iPhone で使い始める前に、次の4項目を実機で確認し、結果を記録する（AC-19）。

| # | 項目 | 要件 |
|---|---|---|
| 1 | 主要アプリでのキーボード互換性 | iAC-02、iAC-06、iOS-02、iOS-09 |
| 2 | キーボード表示遅延・ピークメモリ・バッテリー・発熱・録音から挿入までの遅延 | iAC-09、iOS-PERF-01〜05 |
| 3 | 無断送信なし・ログに本文やトークンを残さない・共有結果の期限切れ削除 | iAC-10、iAC-08、iOS-IPC-05、AC-06、CTX-03 |
| 4 | 本人所有 iPhone へのインストールと継続利用 | iAC-01、12.6節 |

この手順書は **Phase i1・i2 の実装（本体アプリ、キーボード拡張、共有結果の保存）が揃ってから実施する**。現時点ではアプリターゲットがないため、結果欄はすべて空欄（未実施）にしてある。

## 共通の前提

### 端末と環境

- 本人所有の iPhone 1台を主対象とする。機種・iOS バージョン・空き容量を各記録表の冒頭に書く
- Mac の Xcode と Instruments（Xcode 同梱）を使う。計測・監視には公開されているツールだけを使う
- iOS のバージョンを上げたら、項目1と項目2の主要な行を再確認する（Phase 追跡の「iOS バージョン互換性確認」）

### 守ること

- **非公開 API・他製品のクライアント ID・URL スキームの悪用をしない**（AI-02、iOS-03）。検証のためでも使わない
- **iOS の制約を回避しない**（iOS-09、iAC-06）。セキュア入力欄・電話番号欄・サードパーティキーボード禁止アプリで標準キーボードに切り替わるのは正しい動作として記録する
- **iOS のバックグラウンド実行制限を迂回しない**（iOS-PERF-02）。計測のために常時録音やバックグラウンド実行を有効にしない
- 発話・入力には **検証用のダミー文字列だけ** を使う。実在の個人情報、仕事の文章、パスワードを使わない（品質チェック・テスト規約「テストデータ」）

### 検証用のダミー文字列

発話や入力に使う文は、あとでログや通信内容から検索できるように、目印の文字列を含める。

| ID | 内容（例） | 用途 |
|---|---|---|
| D1 | 「ユーターけんしょう いち、きょうは はれです」 | 日本語のみの発話 |
| D2 | 「ユーターけんしょう に、Swift の テストを じっこうする」 | 日英混在の発話 |
| D3 | `UTTERDUMMY0001` | キーボードで直接入力する文字列。ログ・通信の検索用 |
| D4 | `UTTERDUMMYKEY-0000` | 偽の API キーとして設定画面に入れる値（本物のキーの代わり） |

- 目印（`ユーターけんしょう`、`UTTERDUMMY`）は実施ごとに番号を変えてもよい。変えた場合は記録表に書く
- 項目3で実際のクラウド送信を確認する場合だけ本物の API キー・OAuth トークンを使う。そのときもログ検索はキーの全文ではなく、**キーの先頭数文字だけ** を使い、検索結果や記録表にキーを書き写さない

### 記録の置き場所

- 各項目の記録表は本書に書き込むか、実施日ごとに `docs/計測/` へ同じ表を複製して書く（品質チェック・テスト規約）
- Instruments のトレース（`.trace`）、プロキシの通信記録、sysdiagnose、スクリーンショットはリポジトリにコミットしない。端末の識別情報や他アプリの通信を含むため、要約した数値と判定だけを記録する

## 1. 主要アプリでのキーボード互換性（iAC-02、iAC-06）

### 目的

本人が日常的に使うアプリの通常のテキスト欄で utter キーボードを選択・入力・挿入できること、制約のある入力欄では iOS の制約どおり標準キーボードに切り替わることを確認する。

### 前提

- 項目4の手順で utter をインストールし、キーボード一覧に追加済み
- 共有結果（本体アプリの処理結果）を1件以上用意できる状態
- フルアクセスの要否は Phase i0（[Phasei0検証-AppGroup権限.md](Phasei0検証-AppGroup権限.md)）の結論に従う。フルアクセスが必要な構成なら、「有効」と「無効」の両方で確認する

### 対象アプリの選び方

1. 本人が直近1か月に文字入力したアプリを書き出し、入力回数が多い順に並べる
2. 次の分類から各1つ以上を選ぶ（合計8〜12アプリを目安）
   - Apple 標準アプリ: メモ、メッセージ、メール、リマインダー、Safari（アドレスバーと Web ページのフォーム）
   - Web ブラウザ（Safari 以外を使う場合）
   - チャット・SNS アプリ
   - 文書・ノートアプリ
   - 検索欄が中心のアプリ（地図、ストアなど）
3. 制約の確認用に、次も含める
   - パスワード入力欄があるアプリ（Safari のログインフォーム、設定アプリのパスワード欄など）
   - 電話番号入力欄（連絡先アプリの電話番号欄など）
   - サードパーティキーボードを許可しないアプリ（本人が使っていれば。金融系アプリ等にあることがある。特定できなければ「該当なし」と記録する）
4. 各アプリのバージョンを記録する。アプリの更新で挙動が変わるため

### 確認する入力欄の種類

| 種類 | 例 | 期待 |
|---|---|---|
| 1行テキスト | 件名、タイトル | utter を選択・入力・挿入できる |
| 複数行テキスト | メモ本文、メッセージ本文 | 同上。改行キーが改行になる |
| 検索欄 | Safari の検索、アプリ内検索 | 同上。改行キーが検索の確定になる場合はそれを記録 |
| URL・メールアドレス欄 | Safari のアドレスバー、メールの宛先 | 同上（キーボード種別が変わる場合の表示を記録） |
| Web ページの入力欄 | Safari 内のフォーム、textarea | 同上 |
| 数字のみの欄 | 数量、暗証番号以外の数字欄 | 表示されるキーボードを記録する（iOS の判断に従う） |
| セキュア入力欄 | パスワード欄 | **標準キーボードに切り替わる**。utter を出そうとしない |
| 電話番号欄 | 電話番号 | **標準キーボードに切り替わる**。utter を出そうとしない |
| キーボード禁止アプリ | 該当アプリの全入力欄 | **標準キーボードのまま**。utter を出そうとしない |

### 手順

入力欄をタップする前に、上の表で **通常の入力欄か、制約のある入力欄（セキュア入力欄・電話番号欄・キーボード禁止アプリ）か** を決めてから、どちらかの手順だけを行う。

通常の入力欄（表の上6種類）:

1. 入力欄をタップし、地球儀キーで utter キーボードに切り替える
2. ダミー文字列 D3 を通常のキー入力で入れ、削除キー・改行キーの動作を確認する（iOS-08）
3. 地球儀キーで別のキーボードに切り替えられることを確認する
4. 共有結果がある状態でキーボードを表示し、挿入候補が表示されること、挿入操作で1回だけ挿入されることを確認する（iAC-03、iAC-04）
5. 挿入後にアプリの元に戻す操作（シェイクで取り消し、アプリの取り消しボタン等）があれば、挿入が取り消せるかを記録する（必須ではない）

制約のある入力欄:

1. 入力欄をタップし、表示されたキーボードが標準キーボードであることだけを確認する
2. 地球儀キーでの utter への切替、文字入力、挿入は **試さない**。試すこと自体が制約の回避になるため
3. utter のキーボードが表示されてしまった場合は、何も入力せずに入力欄を閉じ、不具合として記録する（iAC-06 の不合格）

### 判定基準

- 合格: 通常のテキスト欄（表の上6種類のうち、アプリに存在するもの）で手順1〜4ができる。制約のある入力欄では標準キーボードに切り替わり、utter 側が回避を試みていない
- 不合格の扱い: 通常のテキスト欄で使えないアプリは、原因（アプリ側の制限／utter の不具合）を切り分けて記録する。アプリ側の制限なら README の既知の制約に載せ、utter の不具合なら Issue にする
- 成功率の数値目標は置かない。iOS では入力先の同一性を保証できないため（iOS-06）、アプリごとの可否を記録することを目的とする

## 2. キーボード表示遅延・ピークメモリ・バッテリー・発熱・録音から挿入までの遅延（iAC-09、iOS-PERF-04）

### 目的

iOS 専用の数値目標（p50/p95、ピークメモリ、10分連続使用時の電力・熱）を設定するための実測値を得る（iOS-PERF-04）。

- **macOS の6章の数値目標を iOS に流用しない。** 判定の基準値としても比較対象としても使わない
- [Phasei0検証-iOSSTT.md](Phasei0検証-iOSSTT.md) の Go 条件（ピーク 2GB 未満など）は Phase i0 の暫定の目安であり、この項目の合否には使わない
- この項目は「計測して記録すること」自体が受け入れ条件（iAC-09）。目標値は計測後に要件定義へ追記する

### 前提

- STT モデル・AI 整形の構成が確定している（Phase i0 の iOS STT 検証の結論後）
- 計測用の区間を `os_signpost`（公開 API）で本体アプリとキーボード拡張に入れてある。区間名は下の「計測区間」に合わせる
- Signpost のメタデータに本文・音声・トークンを含めない。セッション ID や文字数などの数値だけにする（CLAUDE.md プライバシー）
- 計測は Release 構成のビルドで行う（Debug ビルドは最適化が異なるため）

### 条件の固定

各計測の前に次を揃え、記録表に書く。揃えられなかった条件は備考に書く。

| 条件 | 固定する内容 |
|---|---|
| 端末 | 同じ iPhone、同じ iOS バージョン |
| 充電 | 充電ケーブルを外す。開始時のバッテリー残量の範囲を決めて揃える（例: 80〜90%） |
| 低電力モード | オフ（低電力モードでの挙動は別条件として計測する、iOS-PERF-03） |
| 画面 | 明るさを固定し、自動調整をオフ。自動ロックの時間を揃える |
| 通信 | Wi-Fi 接続、または機内モード＋ローカル処理のみ。どちらかを記録 |
| 他のアプリ | アプリスイッチャーから他アプリを終了し、計測前に端末を再起動してから5分待つ |
| 室温・端末の状態 | 室温を記録。ケースの有無を揃える。開始前に端末が熱くないこと |
| マイク | 内蔵マイク（Bluetooth マイクは別条件、6章の扱いと同様に別計測） |
| モデル | ロード済み（ウォーム）と未ロード（コールド）を分けて計測する |
| 発話 | ダミー文 D1・D2 を、毎回ほぼ同じ長さ（約10秒）で読む |

### 計測区間

| 区間 | 開始 | 終了 | 計測場所 |
|---|---|---|---|
| K0 キーボード表示遅延（利用者から見た時間） | 入力欄のタップ、または地球儀キーで utter を選んだ時点 | utter のキーボードが画面に表示された時点 | 画面収録 |
| K1 拡張の内部ロード時間 | 拡張の `viewDidLoad` | キーボードの最初の描画（`viewDidAppear`） | キーボード拡張（Signpost） |
| R1 録音停止→STT 確定 | 停止操作 | STT 最終結果 | 本体アプリ |
| R2 STT 確定→整形完了 | STT 最終結果 | 整形結果（Raw/Local Basic/クラウド AI 別） | 本体アプリ |
| R3 整形完了→共有結果の保存 | 整形結果 | App Group への書き込み完了 | 本体アプリ |
| R4 キーボード表示→挿入候補表示 | キーボード表示 | 挿入候補の表示 | キーボード拡張 |
| R5a 挿入操作→API 呼び出し | 挿入ボタンのタップ | `insertText` の呼び出しが戻った時点 | キーボード拡張（Signpost） |
| R5b 挿入操作→入力欄への反映 | 挿入ボタンのタップ | 元アプリの入力欄に文字が表示された時点 | 画面収録 |

- 本体アプリから元のアプリへ戻る操作は人の手で行うため、時間が人によって変わる。録音から挿入までの遅延は **R1〜R3（本体アプリの区間）と R4〜R5b（キーボード拡張の区間）を分けて記録** し、人の操作の時間は参考値として別に記録する（画面収録の経過時間など）
- **iAC-09 の「キーボード表示遅延」は K0 で判断する。** K1 は iOS が拡張のプロセスを起動するまでの時間を含まないため、拡張内部の改善の目安として別に記録する
- K0 は **コールド** と **ウォーム** に分けて計測する。コールドは、端末の再起動直後など拡張のプロセスが起動していないことを確認でき、その試行で新しく起動したことを記録できたもの（Xcode の Debug → Attach to Process の一覧や Instruments の記録でプロセスの起動を確認する）。別のキーボードを使っただけでプロセスの状態を確認できない試行はコールドに分類しない。ウォームは、直前に utter を表示していて拡張のプロセスが残っているもの
- `insertText` の呼び出しが戻っても、元アプリの入力欄に反映されたことは保証されない。挿入の遅延は R5b で判断し、R5a は拡張内部の処理時間として別に記録する
- K0・R5b は、iPhone の画面収録（コントロールセンター）または別の端末のスローモーション撮影で記録し、開始と終了のフレーム数の差から求める。フレームの間隔（60fps なら約17ms）を誤差として記録表に書く

### 手順

1. **遅延（K0・K1・R1〜R5b）**
   1. Xcode で Release 構成を実機にインストールし、Instruments の「Logging」または「os_signpost」テンプレートで本体アプリとキーボード拡張のプロセスを記録する
   2. 各区間を条件ごとに20回以上繰り返す
   3. トレースから区間ごとの p50 / p95 / 最大を求めて記録する。回数が少ない p95 は参考値と書く
   4. K0・R5b は Signpost の記録と同時に画面収録し、フレームを数えて求める
2. **ピークメモリとプロセス強制終了**
   1. Instruments の「Allocations」と「VM Tracker」（または Xcode の Debug Navigator のメモリ表示）で、キーボード拡張と本体アプリを別々に記録する
   2. キーボード拡張: 表示直後、通常入力を1分続けた後、挿入候補の表示中、挿入後のメモリを記録する。STT モデルを読み込んでいないこと（iOS-PERF-01、iAC-08）も確認する
   3. 本体アプリ: 待機中、録音中、STT 実行中、整形中、処理後30秒のメモリを記録する。処理後に STT・マイクが止まっていること（iOS-PERF-02）を確認する
   4. 強制終了: 計測期間中にキーボード拡張・本体アプリが強制終了した回数を数える。設定アプリの「プライバシーとセキュリティ」→「解析と改善」→「解析データ」の JetsamEvent・クラッシュレポート、Xcode の Organizer、MetricKit（`MXCrashDiagnostic` 等）など公開の手段で確認する。強制終了後に元アプリの入力欄や共有結果が壊れていないことも確認する（iOS-PERF-05）
3. **バッテリーと発熱（10分連続使用）**
   1. 条件を固定し、開始時のバッテリー残量（%）と `ProcessInfo.thermalState` を記録する
   2. 10分間、30秒おきに「録音（約10秒）→ STT → 整形 → 元アプリでキーボードから挿入」を繰り返す
   3. 終了時のバッテリー残量と `thermalState`、端末の触感（ぬるい／熱い）を記録する
   4. 同じ時間、同じ画面状態で utter を使わない対照計測も行い、差を記録する。残量表示は1%単位で10分では差が出にくいため、差が1%以下なら「1%以下」と記録し、次の Power Profiler の値を主に使う
   5. 可能なら Instruments の「Power Profiler」（Xcode 同梱）でも記録し、CPU・GPU・ディスプレイ・ネットワークの内訳を参考値として残す
   6. 計測中に `thermalState` が `serious` 以上になった場合は中止し、その時点までを記録する
4. **待機時**
   1. 本体アプリを開いた後にホーム画面へ戻し、1時間置いて、バッテリー残量の変化を対照計測と比べる
   2. 待機中にマイク使用中の表示（ステータスバーのインジケータ）が出ていないことを確認する

### 判定基準

- この項目は数値の合否を判定しない。次がそろえば完了とする
  - K0・K1・R1〜R5b の p50 / p95 を、ウォーム・コールドそれぞれについて記録した
  - キーボード拡張と本体アプリのピークメモリ、強制終了の回数を記録した
  - 10分連続使用のバッテリー消費と熱状態を、対照計測と並べて記録した
  - キーボード拡張が STT モデルを読み込まず、待機中に本体アプリがマイク・STT を動かしていないことを確認した
- 記録後、iOS 専用の目標値を要件定義 12.5節に追記する Issue を作る（iOS-PERF-04）

## 3. 無断送信なし・ログに本文やトークンを残さない・共有結果の期限切れ削除（iAC-10）

### 目的

- 同意なしに Claude / ChatGPT へ送信しないこと（AC-06）。同意後も、送るのは整形対象の文字列とスタイル区分・辞書語だけであること（CTX-03）
- キーボード拡張がネットワーク送信をしないこと（12.2節）
- システムログ・クラッシュログ・App Group に本文・音声・API キー・OAuth トークンが残らないこと（iAC-08、iOS-IPC-04）
- 共有結果が挿入後・期限切れ後に削除されること（iOS-IPC-02、iOS-IPC-05）

### 前提

- 通信の監視には公開ツールを使う。例:
  - HTTPS プロキシ（mitmproxy などのオープンソースのプロキシ）。iPhone の Wi-Fi 設定で Mac のプロキシを指定し、プロキシの証明書を端末にインストールして信頼する
  - Xcode 同梱の Remote Virtual Interface（`rvictl`）と Wireshark 等のパケットキャプチャ。暗号化された中身は見えないが、接続先のホスト名と通信の有無を確認できる
  - Instruments の「Network」テンプレート（本体アプリの通信の有無と接続先）
- ログの確認には、Mac の「コンソール」アプリ（iPhone を接続して表示）と、sysdiagnose（公開されているログ収集手順）を使う
- 共有結果の期限切れ削除は、`SharedResultStore` の `cleanUp(at:)`（PR #94）を本体アプリの起動時とキーボードの表示時に呼ぶ実装を前提にする。`cleanUp(at:)` は PR #94 で main にマージ済み（d408710）。実施前に、本体アプリとキーボード拡張での呼び出し箇所を確認する

### 手順

#### 3-1. 同意なしに送信しない

1. 本体アプリの同意を「クラウド AI への送信: 同意しない」（初期状態）にする。設定画面に偽のキー D4 を入れておく
2. プロキシとパケットキャプチャを開始する
3. 本体アプリで D1・D2 を5回ずつ録音し、整形まで完了させる。整形方式は Raw / Local Basic になることを確認する
4. 通信記録に `api.anthropic.com`、`api.openai.com`、ChatGPT のサインイン・API 関連ホストへの接続が **1件もない** ことを確認する。目印 `ユーターけんしょう` と `UTTERDUMMY` をプロキシの記録内で検索し、0件であることを確認する
5. Apple のシステム通信（iCloud、OS の更新確認など）は utter の通信ではないため、ホスト名とプロセスで区別して除外する。区別できない通信は備考に記録する

#### 3-2. 同意後に送る内容が限定されている

1. この検証のためだけに発行した、すぐに失効できる API キー（または検証用のアカウントでの Sign in with ChatGPT）でサインインし、送信に同意する。普段使いのキーやアカウントは使わない
2. 発話 D2 を整形し、プロキシで送信内容を確認する
3. 送信内容が、整形の指示（プロンプトの定型文）を除いて、整形対象の文字列とスタイル区分・辞書語だけであることを確認する。入力先アプリ名、既存の本文、URL、端末の識別子が含まれていないこと（CTX-03）
4. 同意を取り消した後、3-1 と同じく送信が止まることを確認する
5. プロキシの記録を保存する必要がある場合は、`Authorization` などの認証ヘッダーとトークンを含む通信を除いてから保存する（mitmproxy なら保存前のフィルタで除外する）
6. 確認後、検証用の API キー・トークンを失効させ、プロキシの記録を Mac から削除する。プロキシの証明書を端末から削除し、Wi-Fi のプロキシ設定を戻す

#### 3-3. キーボード拡張が送信しない

1. フルアクセスを有効にした状態（フルアクセスが必要な構成の場合）で、キーボードから D3 を入力し、共有結果を挿入する
2. パケットキャプチャで、キーボード拡張のプロセスからの通信がないことを確認する（Instruments の Network テンプレートでキーボード拡張のプロセスを選ぶ）

#### 3-4. ログに本文・トークンを残さない

1. コンソールで iPhone を選び、utter の本体アプリとキーボード拡張のプロセスで絞り込んで記録を開始する
2. 3-1〜3-3 の操作に加えて、次の失敗も起こす: マイク権限の拒否、オフラインでの整形、偽のキー D4 での認証失敗、共有結果の期限切れ、キーボード拡張の異常終了（Xcode のデバッガで拡張のプロセスを止める）
3. コンソールの記録と sysdiagnose のログを、目印（`ユーターけんしょう`、`UTTERDUMMY`、D4 の値、本物のキーを使った場合はその先頭数文字）で検索し、0件であることを確認する
4. クラッシュレポート（設定アプリの解析データ、Xcode の Organizer）にも目印が含まれないことを確認する
5. App Group に秘密情報・生音声がないこと（iOS-IPC-04、iAC-08）。ファイルの一覧だけでは中身に紛れ込んだ秘密情報を見つけられないため、中身も検査する。検査は Debug ビルドの開発用の検査機能で行い、**値そのものは画面にもログにも出さず、件数と判定だけを表示する**。検査機能の作り方は Phase i1 の実装時に決める
   1. コンテナ内のファイルを一覧し、想定したファイル（共有結果のファイルと、中身が空のロックファイル）以外がないこと。音声の拡張子（`.caf`、`.wav`、`.m4a` など）のファイルがないこと
   2. 共有結果のファイルを復号し、項目名が想定した項目（`sessionID`、`createdAt`、`expiresAt`、`status`、`text`、`consumedAt` と、実装で追加した revision 等の管理項目）だけであること（iOS-IPC-01）。想定外の項目があれば、値を見ずに項目名だけを記録する
   3. 各項目の値の型と長さが想定どおりであること。たとえば `text` の長さが発話した文の長さと同程度で、音声データを埋め込めるほど大きくないこと
   4. 全ファイルの中身を、D4 の値と、本物のキーを使った場合はその先頭数文字、OAuth トークンの形式に共通する接頭辞で検索し、一致の件数が0件であること（一致した箇所は表示しない）
   5. SQLite を使う構成にした場合は、テーブル名と列名の一覧を同じように確認し、各列を同じ条件で検索する

#### 3-5. 共有結果の期限切れ・挿入後の削除

1. 確認を早めるため、Debug ビルドでは `SharedResultConfiguration(timeToLive:)` で有効期限を短く（例: 60秒）する。Release ビルドの既定値（10分）でも1回は確認する
2. 本体アプリで D1 を処理し、共有結果を保存する
3. 有効期限が過ぎるまで待ち、元のアプリでキーボードを表示する。挿入候補が出ないこと、その共有結果が App Group から削除されていることを確認する。保存方式ごとに確認の対象を分ける: ファイル方式ならその結果のファイル、SQLite 方式ならその結果のレコード（データベースのファイルそのものではない）。ほかの期限内の共有結果が残っていることも確認する
4. 別の共有結果を挿入し、挿入後にその結果（ファイルまたはレコード）が削除されていることを確認する
5. 挿入中に拡張を終了させた場合（猶予時間後に `insertionUnknown` になる）、再表示時に自動で再挿入されず、確認を求めることを確認する（iOS-IPC-03、iOS-IPC-06）
6. ファイル保護（PR #94 で iOS 実機での確認が必要とされた点）。ロック中に読めなくなるのは、共有結果を `.complete` などのファイル保護クラスで保存した場合だけで、既定（`.completeUntilFirstUserAuthentication`）では初回のロック解除後はロック中も読める。そのため、どの保護クラスで保存したかを記録したうえで次を行う
   1. 確認したい保護クラスを指定した Debug ビルドで、本体アプリから共有結果を1件保存する
   2. 端末をロックし、`.complete` の場合はロックから10秒以上待つ（ファイルの鍵が破棄されるまでの時間）
   3. ロック中にキーボード拡張が共有結果を読む操作を行う。ロック画面でキーボードを表示できる操作（通知への返信など）があればそれを使う。ない場合は、ロック中に読む経路がないことを記録して次へ進む
   4. 読み取りの結果を記録する: 挿入候補が表示された（読めた）／表示されない（`SharedResultStoreError.fileAccessDenied` など読めなかった）。どちらの結果かは、拡張の画面表示と、本文を含まないエラーの種類のログで判断する
   5. ロック中に本体アプリの `cleanUp(at:)` が走る場合は、読めなかった結果が削除されず、スキップの件数に数えられることを確認する
   6. ロックを解除し、期限内ならその共有結果が残っていて1回だけ挿入できること、期限切れなら次の整理で削除されることを確認する
   7. 読めない状態を再現できなかった場合は、無理に失敗を起こさず「再現せず」と保護クラスを記録し、共有結果が削除・破損されていないことだけを確認する
7. 端末を再起動した後に本体アプリを開き、期限切れの結果が整理されることを確認する

### 判定基準

- 合格: 次をすべて満たす
  - 同意なしの状態で、クラウド AI の接続先への通信が0件。目印の検索結果が0件
  - 同意後の送信内容が、整形対象の文字列・スタイル区分・辞書語だけ
  - キーボード拡張からの通信が0件
  - ログ・クラッシュレポートでの目印の検索結果が0件。App Group に秘密情報・音声がない
  - 期限切れ・挿入済みの共有結果が削除され、挿入候補に出ない。挿入結果が不明な結果を自動で再挿入しない
- 1件でも不合格なら即修正の対象（CLAUDE.md プライバシー）。Issue にして、修正後に該当の手順をやり直す

## 4. 本人所有 iPhone へのインストールと継続利用（iAC-01）

### 目的

本人の iPhone に Xcode からインストールし、キーボード一覧に utter が表示されること（iAC-01）を確認する。そのうえで日常的に使い続け、項目1〜3では見えない不具合（署名の失効、長期間での共有結果の残り、OS 更新の影響など）を記録する。

### 前提

- Apple Account を Xcode に登録してある。無料 Personal Team か Apple Developer Program かは Phase i0（[Phasei0検証-AppGroup権限.md](Phasei0検証-AppGroup権限.md)）の結論に従う（12.6節）
- 本体アプリ・キーボード拡張・App Group ID の識別子は、README の手順で自分用に設定する（12.6節。README の手順は Phase i1 で追加する）

### インストール手順の概要

1. Xcode で本体アプリとキーボード拡張のターゲットに同じ開発チームを設定し、識別子と App Group ID を自分用に変更する
2. iPhone を Mac に接続し、iPhone 側で「デベロッパモード」を有効にする（設定 →「プライバシーとセキュリティ」→「デベロッパモード」）
3. Xcode で実機を選んでビルド・インストールする
4. 初回は iPhone の「設定」→「一般」→「VPN とデバイス管理」で開発元を信頼する
5. 「設定」→「一般」→「キーボード」→「キーボード」→「新しいキーボードを追加」で utter を追加し、キーボード一覧に表示されることを確認する（iAC-01）
6. フルアクセスが必要な構成なら、理由の案内を読んだうえで有効にする。無効のときの制限表示も確認する（iAC-07）
7. 本体アプリを起動し、マイク・音声認識の権限を許可する

- 無料 Personal Team ではプロビジョニングが通常7日で失効し、再インストールが必要。有料の Developer Program でも更新は必要（12.6節、ビルド・配布規約）
- 証明書・プロビジョニングプロファイルはコミットしない（ビルド・配布規約）

### 継続利用の期間と記録の取り方

- 期間: **最低14日**（無料署名の場合、7日の失効と再インストールを1回以上含めるため）。この期間は提案であり、実施前に本人が決めて記録表に書く
- 毎日の終わりに、その日の利用を1行で記録する。記録するのは回数と事象だけで、**発話や入力の内容は書かない**
- 次のことが起きたら、その日の備考に書く
  - キーボードが表示されない、標準キーボードに戻ってしまう
  - 挿入候補が出ない、二重に挿入された、違う欄に挿入された（iOS-06）
  - 本体アプリ・キーボード拡張の強制終了
  - 署名の失効、再インストール（日付と所要時間）
  - iOS の更新（更新後に項目1の主要な行を再確認する）
  - 端末が熱くなった、バッテリーの減りが気になった
- 不具合は再現手順を整理して Issue にする。Issue には発話内容を書かない

### 判定基準

- iAC-01 の合格: Xcode からインストールでき、キーボード一覧に utter が表示される
- 継続利用の完了: 決めた期間を使い終え、記録表が埋まっている。二重挿入・無断送信・データ破損が0件であること。0件でなければ Issue にして修正後に期間をやり直す
- 本人端末での運用開始（Phase i3 の完了）は、項目1〜4がすべて完了した時点で判断し、[Phase追跡-PR完成度.md](Phase追跡-PR完成度.md) に記録する
