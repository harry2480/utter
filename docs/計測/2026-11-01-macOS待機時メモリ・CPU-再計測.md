# macOS アプリの待機時のメモリ・CPU（画面をそろえた再計測、2026-11-01）

Phase 0 検証 [#52](https://github.com/harry2480/utter/issues/52) の「待機時メモリ・CPU」の再計測。[2026-10-31 の記録](2026-10-31-macOS待機時メモリ・CPU.md)は、A（STT 未選択）の画面の状態を確かめておらず、A と B の差を比べられなかった。今回は A・B とも、起動直後に開いたウィンドウを閉じてメニューバーだけにし、ウィンドウの数を記録してから測った。

要件定義 6章の目標は、待機時アプリメモリ ≤ 50MB、待機時 CPU 平均 ≤ 0.1%。

## 条件

- 実行日：2026-11-01（A は 21:40〜22:09、B は 22:15〜22:50）
- 機種：Mac17,2・Apple M5、macOS 27.2（26B123）
- 電源：A・B とも**バッテリー駆動**（`pmset -g log` で 21:03〜22:39 は `Using Batt`、残り 31% → 23%）。低電力モードはオフ。2026-10-31 の記録（AC 電源）とは電源の条件が違う
- アプリ：`Apps/macOS` の Release 構成（main の `2cd78ec`）。2026-10-31 と同じく、署名なしでビルドしてアドホック署名した
- 起動 15 秒後に、A・B とも「初回セットアップ」のウィンドウが1つ開いていた。System Events で閉じるボタンを押してウィンドウを 0 にし、5 分置いてから `sample-process.sh` で 60 秒ごとに 30 分記録した。記録の前と後でウィンドウが 0 であることを確かめた
- 録音・認識は一度もしていない。計測の前後と、待機の5分の間に毎分、STT Worker（`UtterSTTWorker`）が起動していないことを `pgrep` で確かめた（A・B とも起動していなかった）
- ほかのアプリ（ブラウザ・エディタ・Xcode のビルドなど）は普段どおり動いていた

| 計測 | 音声認識の設定 |
|---|---|
| A | 未選択（`UTTER_MAC_STT_ENGINE=`） |
| B | SpeechAnalyzer（`UTTER_MAC_STT_ENGINE=speechAnalyzer`）。utter の設定画面でモデルの取得（ロケールの予約）はしていない |

再現のコマンドは [2026-10-31 の記録](2026-10-31-macOS待機時メモリ・CPU.md)と同じ。違いは次の3点。

```sh
# 1. 起動後、utter のウィンドウを閉じる（手で閉じてもよい）。数が 0 になったことを確かめる
osascript -e 'tell application "System Events" to tell process "utter" to repeat with w in (every window)
  click (first button of w whose subrole is "AXCloseButton")
end repeat'
osascript -e 'tell application "System Events" to count windows of process "utter"'
# 2. 記録の対象は utter だけにする（待機中は STT Worker が起動していないため。
#    sample-process.sh は起動していないプロセスを --name で渡すと、記録を始めずに終わる）
scripts/sample-process.sh --name utter --interval 60 --duration 1800 --output out/idle-a.csv
# 3. 計測中に Mac がスリープしないようにする（下の「B の後半」を参照）。蓋を閉じない、または caffeinate -i を併用する
```

## 結果

| 計測 | 使った区間 | メモリ（Physical footprint） | CPU 平均 | 6章の目標 |
|---|---|---|---|---|
| A（STT 未選択） | 30 分（1,760 秒、29 区間） | 32.7〜32.8MB | 0.003% | ≤ 50MB・≤ 0.1% → **どちらも内** |
| B（SpeechAnalyzer） | 約 24 分（22:15〜22:39、24 区間。スリープの前まで） | 33.1〜34.0MB | 0.016% | 同上 → **どちらも内** |

- 画面をそろえると、A と B のメモリの差は 1MB 未満だった。2026-10-31 の記録の約 18MB の差（A 38.8〜39.0MB、B 19.2〜21.2MB）は、STT の設定の差ではなかったと見られる。ただし 2026-10-31 の A で、実際にウィンドウが開いていたかは確かめられない。また電源の条件も違う（推測）
- どちらも 30 分の間（B は 24 分の間）、メモリは増え続けなかった
- CPU は B のほうが高い（0.003% と 0.016%）。どちらも目標の 1/6 以下で、1 分ごとの値の最大は A が 0.016%、B が 0.049%（スリープの前まで）。B は電池の残りが少ない時間帯（27% → 23%）で、ほかのアプリの負荷も同じではないため、STT の設定による差かは分からない

### B の後半（スリープと復帰）

22:40:03 に Mac の蓋が閉じ（`Clamshell Sleep`）、スリープと復帰（DarkWake）を繰り返した。この時間帯の値は待機時の値として使わず、上の表から除いた。

- 22:40 のサンプルで、メモリは 33.1MB → 37.0MB、その 1 分の CPU は 0.424% になった。それ以降は 37.0MB のまま、CPU は 0.000% だった
- 22:43:48 の次のサンプルは、スリープのため 22:50:22 まで取れなかった（394 秒の間隔）
- スリープ・復帰のときに utter が何をしたか（メニューバーの再描画、ショートカットの登録し直しなど）は確かめていない。復帰のたびにメモリが増え続けるかは、スリープと復帰を繰り返す計測で別に確かめる

## 測れていないこと

- AC 電源での、画面をそろえた A・B（2026-10-31 との電源の条件の違いを埋める）
- 開発用署名（`build-local.sh`）のビルドでの値
- utter の設定画面でモデルを取得した（ロケールを予約した）状態の B
- スリープ・復帰を繰り返したときのメモリの推移
- 録音開始遅延・停止→挿入（Signpost）、録音中・認識中のメモリ、8時間待機の追加バッテリー消費、Bluetooth マイク
