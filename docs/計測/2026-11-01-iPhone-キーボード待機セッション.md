# iPhone でのキーボードの待機セッション方式（Typeless 型、2026-11-01）

[#233](https://github.com/harry2480/utter/issues/233) の検証の記録。キーボードの🎤で、裏で待機している本体アプリに録音・認識・整形をさせ、結果をキーボードが入力欄に挿入する形が成り立つかを、試作（[iOSKeyboardProbe](../../Verification/iOSKeyboardProbe/README.md)）で確かめた。

**声は Mac のスピーカーから流した合成音声で、人の声での精度の代わりにはならない。** 認識の精度は [#54](https://github.com/harry2480/utter/issues/54) の記録を参照。この記録で見るのは、合図・録音・挿入の流れと時間、待機の持続、異常時の扱い。

## 条件

- 実行日：2026-10-31〜2026-11-01
- 機種：iPhone 17 Pro（`iPhone18,1`）・iOS 27.2
- 署名：無料の Personal Team（App Group 有効）。Debug ビルド。Mac からケーブルでつないだまま（充電中）
- 試作の構成：本体アプリ（utter Probe）とキーボード拡張。キーボードはマイク・STT を持たない（iAC-08）
  - **合図**：App Group のファイルと Darwin 通知。キーボードから本体アプリへの開始・停止・取り消し
  - **認識と整形**：`SpeechAnalyzer`（`ja_JP`）と Local Basic
  - **結果の受け渡し**：`SharedResultStore` と `SharedResultInsertionCoordinator`（utter 本体と同じ Package）
- 入力先：メモアプリの新しいメモ（他社製キーボードを選んだ状態）
- 待機の無操作での終了：UI テストでは切った（`-ProbeIdleTimeoutMinutes 0`。既定は5分）
- 自動化：XCUITest（`Verification/iOSKeyboardProbe/UITests/`）。キーボードの中は UI テストから見えないため、キーボードが App Group に書くボタンの位置を座標でタップし、計測の記録（時刻と区間名だけ）で判定した
- 待機の方式（本体アプリが裏で待つやり方）
  - `holdMicrophone`：マイクを開いたまま待ち、合図までの音声は捨てる
  - `mutedMicrophone`：マイクを開いて、合図まで `AVAudioApplication.setInputMuted(true)` でミュートする
  - `silentPlayback`：無音を再生して待ち、合図でマイクを開く

再現のコマンド（リポジトリのルートで実行。前提は試作の README）：

```sh
Verification/iOSKeyboardProbe/run-ui-tests.sh testTwentyCycles testPreviewThenInsert
Verification/iOSKeyboardProbe/run-ui-tests.sh testStandbyEnduranceMuted   # 約31分
```

## 結果

### 流れと時間

回ごとの結果（「診断」は、挿入の前後の文脈の文字数などを記録するようにした後か）：

| 順（11/1） | テスト | 方式 | 診断 | 挿入できた回 | 認識結果が空 | `insertionUnknown` |
|---|---|---|---|---|---|---|
| 1 | `testTwentyCycles` | holdMicrophone | 前 | 18/20 | 2 | 0 |
| 2 | `testStandbyEnduranceMuted`（5分後・30分後の2回） | mutedMicrophone | 前 | 1/2 | 0 | 1（30分後） |
| 3 | `testTwentyCyclesMuted` | mutedMicrophone | 前 | 15/20 | 4 | 1 |
| 4 | `testTwentyCycles` | holdMicrophone | 前 | 15/20 | 4 | 1 |
| 5（14:32 開始） | `testFortyCycles`（20回×2） | holdMicrophone | 後 | 39/40 | 1 | 0 |

時間（挿入できた回だけの値。1回のテストは20回以下）：

| 測ったもの | holdMicrophone | mutedMicrophone |
|---|---|---|
| 二重の挿入 | 0回（計80回） | 0回（計22回） |
| 🎤を押してから録音が始まるまで（中央値） | 6〜7ms（最大 14ms） | 18ms（最大 21ms） |
| 停止を押してから挿入まで（中央値） | 66〜70ms（最大 135ms） | 78ms（最大 116ms） |

- 合図は、本体アプリが裏（background）にいる間も毎回届いた
- **挿入できなかった回のほとんどは、認識結果が空だった**
  - 拾えた音の最大音量が 0.02 前後と小さく、合成音声の切れ目に当たったため。待機の方式による差は見えない
- **102回のうち3回、挿入の命令を出したのに文字が入らなかった**（`insertionUnknown`。メモの文字数も増えていない）
  - 二重挿入を防ぐ仕組みが「入ったか確認できない」として扱い、自動では入れ直さなかった（iOS-IPC-03 のとおり）
  - 3回とも、診断の記録を足す前に起きた。足した後の40回では起きなかったので、原因は分かっていない

### 待機の持続

- **mutedMicrophone で30分待機した後も、待機は続いていた**（🎤→録音開始 19ms）
  - 5分後は挿入できた
  - 30分後は認識・保存まで進んだが、挿入は上の `insertionUnknown` になった（診断の記録を足す前）
  - 画面は点けたまま（1分ごとにタップ）。充電中で、画面を消したときの持続と電池の減りは測っていない
- silentPlayback では、裏でマイクを開けなかった（`avfaudio` 2003329396、2026-10-31）。この方式は使えない

### 待機中のマイクの表示

- holdMicrophone では、待機中ずっとオレンジの点が出る
- **mutedMicrophone では、待機中と停止後はオレンジの点が出ず、録音中だけ出る**（スクリーンショットで確認）。入力もできる
- Wispr Flow も、録音を止めると点は消え、待機は Dynamic Island の表示として残すと説明している（[Wispr Flow のヘルプ](https://docs.wisprflow.ai/articles/3634682593-why-the-orange-dot-or-mic-indicator-stays-on-after-dictating-ios)、2026-07-17 更新）

### キーボードから本体アプリを開く（iOS-03、#53）

| 手段 | 結果 |
|---|---|
| `extensionContext.open` | 開かない（2026-10-31 の #53 の記録と同じ） |
| SwiftUI `openURL`（`OpenURLAction`） | **開く**（フルアクセスあり。UI テストで本体アプリが前面に出た。手でも確認） |

### 異常時

| 状況 | 結果 |
|---|---|
| 録音中に本体アプリを強制終了 | キーボードは20秒待って「結果が届きません」と出し、何も挿入しない。次の🎤では「待機していません」と案内する |
| 録音中にロック・ホーム画面へ出る | **試作の当初の作りでは、本体アプリが画面に何も出さないまま録音を続け、次の録音も始められなかった。** キーボードが閉じられるときに取り消しを送り、本体アプリが録音を捨てるように直した。直した後は、ロックでもホーム画面へ出る操作でも録音を捨て、戻るとすぐ入力できた |
| 停止の合図が来ないまま録音が続く | 上限（既定120秒、テストでは10秒）を超えたら本体アプリが録音を捨て、キーボードに「失敗: 録音が◯秒を超えた」と出る |
| 自動挿入をオフ | プレビューが出て、勝手には入らない。「挿入」で1回だけ入る。アプリを切り替えて戻ってもプレビューは残る |
| ロックの後にキーボードが反応しない | 手で試した1回だけ起きた。キーボードを閉じて出し直すと直る（[#244](https://github.com/harry2480/utter/issues/244)） |

## 未確認

- 画面を消した状態での待機の持続と、待機中の電池の減り（ケーブルを外す必要がある）
- 録音中の着信（電話・LINE 通話）の割り込み（[#243](https://github.com/harry2480/utter/issues/243)）
- 人の声での認識と、Bluetooth マイク
- `insertionUnknown` の原因
- メモ以外のアプリ（Slack・LINE・Safari など）での挿入
- キーボード拡張が、取り消しを送れないまま強制終了された場合（今の試作では、本体アプリは録音の上限まで録音を続ける。要件の案では、キーボードの生存の印が途絶えたら捨てる）
- 停止後、挿入までの間にキーボードが閉じられた場合（試作は、録音中に閉じられたときしか取り消さない）
- フルアクセスなしで、キーボードから本体アプリを開けるか
- ミュートの間に、マイクの入力の音声（無音）が届き続けるか（試作は、合図の間以外は認識器に渡さずに捨てる）

## 判定（案）

- **待機セッション方式は成り立つ。** 2回目以降は本体アプリへ移らずに、キーボードの🎤だけで録音を始め・止めて挿入できる。時間は、6章の macOS のストレッチ目標（録音開始 p95 ≤ 200ms、ローカルの停止→挿入 p50 ≤ 300ms）も下回る（iOS-PERF-04 により iOS へは流用しない。参考）
- **待機の方式は mutedMicrophone を既定の候補にする。** 待機中にマイクの表示が出ず、録音開始の遅れも約20msにとどまる
- **待機していないときは、キーボードから SwiftUI `openURL` で本体アプリを開ける。** ただし将来の iOS で変わりうるため、開けないときの手動切替の案内を残す
- **録音中にキーボードが閉じられたら、録音を捨てる仕組みが必須。** ないと、画面に何も出ないまま録音が続く
- **iOS-PERF-02・03 とぶつかる。** 待機中はマイクの入力を開いたまま（mutedMicrophone でもミュートしているだけ）で、オーディオのバックグラウンドモードで本体アプリを保つ。今の要件は「待機時にマイクを常駐させない」「バックグラウンドモードを常時録音のために使わない」としている。待機は利用者が明示的に始め、無操作で終わり、合図の間しか認識しない形にして、要件の側を改める案を出す
- 要件の書き直し案は、同じ PR の `docs/要件定義.md` の変更を参照
